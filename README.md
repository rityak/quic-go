# quic-go

Реализация QUIC. В miray на ней работают hysteria2 и tuic.

Форк [metacubex/quic-go](https://github.com/metacubex/quic-go) для [miray](https://github.com/rityak/miray). Наш код — в ветке `miray`.

## Что изменено

- Переполненный буфер сокета (ENOBUFS, EAGAIN) — отправка повторяется. Пропавший маршрут (ENETUNREACH и похожие) — пакет считается потерянным. Раньше любая такая ошибка закрывала соединение.
- Очередь входящих пакетов соединения 4096 вместо 256: под нагрузкой пакеты больше не отбрасываются на приёме.
- Windows: отправка пачкой через USO (`UDP_SEND_MSG_SIZE`) и приём нескольких датаграмм за чтение (`UDP_RECV_MAX_COALESCED_SIZE`).
- Linux: в одну GSO-пачку идут и одинаковые пакеты меньше максимального размера. Раньше склеивались только полноразмерные, а пакеты с UDP-датаграммами почти всегда меньше — каждый уходил отдельным `sendmsg`. UDP через hysteria2 и tuic: CPU клиента −14%, сервера на загрузке −9%.
- GREASE QUIC bit (RFC 9287): если пир поддерживает, половина коротких пакетов уходит со сброшенным фиксированным битом.
- Исправлено приведение указателя в USO-отправке: под `-race` процесс падал на `checkptr`.
- Принятая QUIC-датаграмма больше не копируется дважды: на каждую было две копии и две аллокации, теперь одна.
- Linux: приём через UDP GRO — ядро отдаёт пачку пакетов одного потока за раз, они режутся по размеру сегмента. TCP через hysteria2 и tuic дешевле по CPU на 16–19% (бенчмарк в одном процессе). Выключается `MIRAY_QUIC_GRO=off`.
- Датаграммы больше не забивают потоки. Раньше датаграмма клалась в пакет первой и не оставляла места данным потоков: пока датаграммы стояли в очереди, потоки и повторные отправки ждали. У tuic так застревала аутентификация, и сервер терял датаграммы начала сессии (потери на старте −59% на стенде). Теперь, когда ждут и те и другие, пакеты чередуются.
